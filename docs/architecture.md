# Architecture

Second Star Online is a server-authoritative browser remake of First Star Online 1.6 that fixes its exploits and bugs but keeps the feel of the original. The [system guides](guides/README.md) describe the implemented behavior; deliberate differences, fixed bugs and bugs kept on purpose are documented in [differences from 1.6](differences-from-fso.md).

## Packages and boundaries

- `packages/shared` contains protocol schemas and pure rules used by server and client prediction.
- `packages/server` contains the gateway, simulation, SQLite persistence, migrations and operator commands.
- `packages/client` is plain TypeScript, DOM and Canvas2D, without a UI framework.
- `packages/data` contains editable content, strict schemas, generated game modules and the asset build.
- `packages/perf` contains load bots and performance scenarios.

Outside the packages, `tests/` holds repository-wide checks (import boundaries, documentation paths and tables, pinning-test names), which `bun run test` runs first, and `tools/` holds maintenance scripts that are not part of the game (see [tools](../tools/README.md)).

Bun runs the server, bundles the client and runs tests. A single production process serves the prebuilt client and WebSocket from the same origin; the container runs as a non-root user. See [running a server](running-a-server.md) for deployment, proxy settings and operational details.

Rules and simulation use plain functions with dependencies passed in. The gateway owns sockets and message validation; persistence modules own SQL; startup wires the database, clock, random source and send functions together. Systems receive their dependencies rather than importing gateway or persistence modules. Shared imports only data and Zod; the client does not import the server. Tests enforce these boundaries. Test fixtures are not production dependencies.

## Simulation and protocol

The server runs a fixed 20 Hz simulation. Active maps are rooms with their own players, monsters, tiles, items and effects. Each frame applies the actor phase twice in its established order, then the frame logic and ensuing map changes and updates. Rules use injected randomness and clocks so seeded replays can reproduce outcomes. Gameplay cadence is enforced by the simulation.

Messages are JSON over WebSocket. Zod validates inbound messages; clients send intents and the server determines outcomes. Sender identity comes from the authenticated session. The server sends a snapshot on map entry and subsequent updates, acknowledgements and movement corrections. Token buckets limit incoming intent rates. Account roles come from the database, and privileged commands and editor writes are validated on the server.

Passwords use Bun's Argon2id support. Sessions can resume after a temporary disconnect. Login, creation and socket limits are enforced at the gateway; operators can configure trusted proxy hops. State-changing operations execute in SQL transactions; failures roll back SQL and the affected session reloads its state on login.

## Persistence and settings

SQLite uses WAL mode and migrations. Database access is synchronous and grouped by area in plain persistence modules. Primary keys use UUIDv7 except for parent-keyed value tables and migration bookkeeping. Accounts and characters are separate; current play creates one character with its account. Gold or item movement is atomic. Economy changes, deaths and progression are written through; vitals and position also receive periodic saves.

Stored data includes characters, inventory, maps and versions, NPC files and versions, shops, houses, guilds, mail, boards, social lists, settings and administrative logs. Editor saves are validated, and saved NPC files override the seed data. Settings have typed defaults and are applied when saved. Admin commands (except `/inventory`, `/location` and `/banlist`, which only show the staff member their own bag, place or the ban list), world and NPC editor saves, setting changes, role changes and Assassin's Game mode changes are audited; newspaper saves are not. Bans, jails, IP bans, mutes, pardons and their lifting go to a separate moderation log, which `/auditlog` reads alongside the audit log.

## Content and assets

Second Star Online is an engine; the 1.6 content is the **Classic pack**. Every rule, system and client module reads content through one live content store in shared (`content()`), never from a compiled-in module. Installing a new store swaps it in one step, and the values modules derive from it (text tables, flag sets, indexes) are rebuilt by `onContent` callbacks as live `export let` bindings, so a publish reaches everything. A repository test imports every module with no store installed, so none can keep a load-time copy.

The server builds the store at start-up from the installed packs (`content_packs`, in load order) with the operator layer on top (`content_rows`: per-row changes, additions and removal markers, each with the hash of the pack row it was based on). The Classic pack ships in the release and is read from the image (`packages/data/packs/classic/`), never copied into the database, so a release fix reaches it; an imported pack is stored in the database as a read-only layer. The Packs page exports the operator layer as a pack file and imports one, merged into the draft or installed as a pack in play from the next start (issue #34); an imported pack that would stop a start is left out, so the Control Panel can remove it. Operators change content on the Control Panel's content pages, one page per part of the content, each form drawn from the row's schema (`client/ui/content-areas.ts`, `content-area-page.ts`, `schema-form.ts`): changes collect in one shared draft (each save naming the row's revision, so a save over a newer change is refused), are checked (schemas, then the key and name rules, then cross-references), and are published from the Publish Changes page in one transaction that swaps the store live and can be undone as a whole. When a release ships a newer pack version, rows the operator has not changed pick it up; a changed row keeps the operator's version and shows a notice.

The client bundles no content. It fetches the published store from `/content/<hash>.json` (cached for good, since a hash names one store) when it starts, and again when the login message or a publish names another hash; messages wait until the new store is installed. NPC file text and collision rects stay on the server.

Edit the JSON in `packages/data/content/` and run `bun run data:build`. The build validates strict schemas and writes the Classic pack (`packages/data/packs/classic/`: a manifest and one file per dataset), bumping its version whenever its content changes, plus the seed maps' modules; both are committed. `bun run data:check` detects stale output. The [modding guide](modding.md) explains content editing and the release fingerprint baseline.

The asset build reads retained bitmaps, sound and layout metadata in `assets/original/`, plus additions in `assets/added/`, and generates the engine's art (the UI files and the interface's click sounds, in `packages/data/assets/`) and the Classic pack's art (its atlases and sounds, in `packages/data/packs/classic/art/`), each with an index. The server serves the engine's art and the art of every installed pack (under `/assets/packs/<id>/`), merging their indexes into the `/assets/index.json` clients load, so a server without the Classic pack never sends 1.6 art. Atlases are build output and are not edited by hand. Sprite positioning uses member dimensions and registration points; unstretched sprites use their member's size. Added art uses a sidecar with its group and registration point. The data build derives server collision rectangles from retained and added art. The PNG codec, keying, north-frame mirroring and the packer live in `packages/data/src/art/`, shared by the asset build and the server.

The game's global balance numbers (spell amounts and buffs, regeneration, hunger and death, death drops and loot, timings, combat rolls, hull wear and the cannon; issue #19) are the server-only `balance` dataset. Every value has an engine default (`shared/content/balance.ts`, `BALANCE_DEFAULTS`), and the store fills any part a world leaves out from it, so `content().balance` is always whole; rules read it there instead of constants. The Control Panel's Game Rules page (with the spell cards on Spells and the vehicle card on Houses & Vehicles) edits its rows through the shared draft (`server/content/balance.ts`). Settings that became balance values move once at start, as a logged publish (`server/content/moved-settings.ts`).

World events (issue #3) are the server-only `events` dataset: counters, offerings and counter perks, edited on the Control Panel's World Events page. Their rules are pure (`shared/rules/world/events.ts`); the counters' values are world state (`world.counters`), saved in `world_counters` in the same transaction as the bags an offering changes, reconciled with the store at start and after each publish, and passed into the caster and fighter a fight builds.

Operators upload art and sounds too (issue #29). An upload is posted over HTTP with a ticket from the Control Panel, checked, and stored in `<database name>-content/` beside the database under its SHA-256 (`persistence/art-files.ts`); rows of the server-only `art` dataset name the files, so uploads go live, and are undone, with the draft's publish. Each publish builds the published rows into one atlas per group in memory (`content/art.ts`, `ArtLibrary`), lays their trimmed hit rects over the packs' `rects`, and rebuilds the served index once (`content/served-assets.ts`): the engine's art, each pack's under `packs/<id>/…?v=<input hash>`, and the operator's sheets and sounds under `operator/`, named by content hash, so every art URL can be cached for good. The `content` message carries the index's hash; a client loads the index again and only the sheets and sounds that changed before it handles the messages that follow. A pack may carry art rows of its own and the files they name (`files/`, each a regular file inside the pack, checked against its hash when read, and read only for hashes its rows declare). At start the server builds each pack's rows, from that pack's own files only, into a layer served under `operator/packs/<id>/`: over that pack's atlases, under the next pack's and the operator's. Hit rects and the packs' sprite and sound keys are folded in the same order (`packArtLayers`). A row with a file missing or damaged is left out whole and listed under Publish Changes' Find problems.

## Client

The client starts by fetching the server's content store, then uses a 544×384 logical canvas for the playfield and DOM components for controls and windows. The game frame scales as a unit; floating windows scale with it. The client predicts movement and the attack lock using shared rules, then reconciles with the server. Combat results, loot and economy outcomes remain authoritative. Input uses the established directional priority and sends intents; interactive DOM controls carry semantic action identifiers.

## Tests and dependencies

`bun run gate` runs type checking, lint, tests and generated-data checks. The suite includes rule tests, seeded simulation replays, real in-memory SQLite tests, happy-dom client tests and bot end-to-end tests against a server. Differences from 1.6 have named pinning tests linked from the differences document. Changes to the interface should also be checked in a browser.

Prefer web-platform and Bun built-ins. Zod is the runtime validation dependency (also of `packages/data`, whose schemas the build and the server's content store validate with); TypeScript, Biome, Bun types, happy-dom and its global registrator (`@happy-dom/global-registrator`, which installs the DOM for client tests) are development dependencies. Add a dependency only with its reason documented here.
