# Admin

## What happens in play

Staff hold a role that the operator defines: by default a moderator can kick, ban, jail and mute players, while an administrator can also warp, edit the world and change the server's settings and roles. The server checks the role's permissions before it acts.

## How it works

The server routes administration requests through `handleAdmin` and checks permissions using `can`. Commands also record audit information. Login limits track attempts by IP and account and limit character creation.

### Roles

A role has an id, a display name, a rank and a set of permissions: one per admin command and tool, plus the gameplay exemptions (takes no damage, never hungry, cannot be pushed, off the high scores, not stopped by IP bans or login limits, drops on every death, and skips the chat or broadcast cooldown). The operator's roles live in the database's `roles` table; a new server starts with `moderator` (Moderator, rank 1) and `administrator` (Admin, rank 2). An account holds at most one role, and an account with none is an ordinary player: rank 0, no permissions. Any role makes an account staff, so it reads and posts staff chat and can be sent IMs by jailed and muted players. Nothing checks a role by name. The client receives only its permissions, to decide which menus to show, and the server checks every request.

Roles are edited on the Server Settings page's Roles page and given to accounts on its Staff page, both gated by the `settings` permission, or with `bun run admin:role <name> <role|none>` (and `--list`). There is no in-game command for it. A change made in Server Settings applies at once to everyone online who holds the role: they get their new permissions, a `/warpscript` they may no longer use is cleared and an editor or the Control Panel they may no longer use closes (`applyRole`, `mayEdit`), and on the next tick they leave a room such as Admin Chat they may no longer use (`roomMembership`). A change made with `bun run admin:role` takes effect at the account's next login. Deleting a role leaves its accounts with no role. At least one role must keep every permission (`rolesError`), and nobody can change their own role on the Staff page, so the server can always be run; the command line can always give a role. Every role edit, deletion and assignment is written to the audit log.

The Chat page's Role tags setting (off by default) puts the speaker's role name before their name in local chat, `/me`, broadcasts, chat rooms, guild chat and staff chat: `[Admin] Berlyn says "hi"` (`taggedName`). IMs keep the plain name, since it is the address a reply goes to, and ignore lists still match the plain name.

### The Control Panel

The Control Panel is a full-page dashboard in the client, opened from **Admin → Control Panel** by a role holding a permission in `CONTROL_PANEL_PERMISSIONS` (today `settings`, `characterView`, `activityLog` and `contentEditor`; each Control Panel page adds its own). The server checks it again (`canOpenControlPanel`) and writes a refused `controlPanelOpen` to the cheat log. Opening it works like the World Editor: `openControlPanel` calls `leaveForEditor` with `"controlPanel"`, so the admin stays online but leaves the map (everyone there sees them go, trades, shops and held actions are cancelled, nothing on it ticks for them). Return to Game sends `editClose`, and `closeEditor` puts them back where they stood with the login i-frames. While in the Control Panel the server takes only `EDITOR_INTENTS`: the editors', the Control Panel's pages' and the floating windows' (IM, Away, chat rooms, Friends, Bio, Who's Online and Player Settings).

In the client the Control Panel replaces the game view and its classic menu bar. Its header has Return to Game, the floating-window tools (with a count of IMs that arrived while it is open) and Return To Title Screen; its sidebar lists the pages your role may use, by group (groups in the order their first page is listed, pages A–Z within each), and opens on the top one. The floating windows use their own size over the Control Panel instead of the 800×600 frame's scale. A page reports its unsaved changes, and leaving it asks first. Each page's own requests are still gated by their permission on the server (`ADMIN_INTENTS`). `characterEditor` gates the hub's editor; `contentEditor` gates every kind of content, maps and NPC files included: the content pages (the sidebar's Content and Publishing groups), the NPC file editor (`contentNpcs`, `contentNpcSave`) and the World page. The World Editor's and NPC Editor's own permissions (`worldEditor`, `npcEditor`) were folded into it, and a migration gave `contentEditor` to every role that held either. The NPC file editor is the Creatures & NPCs page's Talk & Shops tab, which replaced the frame-311 NPC Editor window (issue #32): its saves are checked as that window's SAVE was (`checkNpcFile`), name the revision they started from, and apply live. The World page (`contentMaps`, `contentMapSave`, `contentMapRestore`) replaced the in-game World Editor (issue #33): a save is checked as its SAVE was (`saveError`), applied live (`applySave`) and versioned, and names the revision it started from (`mapRevisionOf`: the editor's view and the newest version's id, so an unchanged save or a restore still moves it on). Like every Control Panel page's, these requests are gated by their permission, not by the panel being open.

### The content store

Every rule reaches content through the shared content store (`content()` in `packages/shared/src/content/store.ts`). The server's `ContentService` (`packages/server/src/content/service.ts`) builds it at start-up from the installed packs (`content_packs`; Classic is read from `packages/data/packs/classic/` in the release) and the operator layer (`content_rows`), and installs it before the game loads. A dataset's top-level field is either a keyed list, whose entries are rows by key (`KEYED_LISTS` in `content/rows.ts`: items and monsters by name, NPC files, spells, help topics, classes, skills, start classes, deeds, house types, factions), or one row of its own. Operator rows never edit pack rows in place: a change, an addition or a removal marker sits on top, with the hash and JSON of the pack row it was based on.

The content pages' intents (`contentOverview`, `contentList`, `contentRow`, `contentDraft`, `contentDiscard`, `contentPublish`, `contentUndo`, `contentNotice`, `contentUsage`, `contentRemove`, `contentProblems`; `content/page.ts`) need `contentEditor`. A draft change must keep its dataset valid against its schema; a publish runs every check (`content/validate.ts`: schemas, then the key and name rules and the skill rules (no two keys alike once case and spaces are ignored, and a published key keeps its exact spelling; skills may be added, removed or reordered, since characters save each under its key), then the references a change breaks, item, monster and skill names alike, compared with the published store so Classic's own unresolved names are not reported, except a skill binding to no skill, which is named every time), then, once the schemas pass, the content contract (`content/contract.ts`: a currency item, a start class, a skill, rider bodies that differ, no tree, smoke or morph body that is a rider's or another of those, and the start, fallback and jail points on walkable ground a new character may stand on, judged with the draft's tiles inside the trial install through the game's `contractPointProblems`; named every time, first), refuses a draft another admin changed since it was read (the overview's `draftRev`, a hash of every change in the draft, comes back with the publish), trial-installs the result (every module rebuilds from it, then the installed store goes back) so a row a rule cannot read is refused before it is written, writes the operator rows, the publish log (`content_publishes`, each row's state before and after) and an audit entry in one transaction, then swaps the store in. A `contentPublish` with `logoutEveryone` (issue #40) goes through `publishAlone` in `game.ts`: once the publisher's permission and `ContentService.publishPreflight` pass (run inside its own catch, so a throw is a fault as in any intent; every check the publish runs before it writes: an empty or changed draft, the draft's checks with its retirements and orphans settled against the world, and the maps' tiles; the publish itself runs the same `publishPlan`), it sets the publish lock and logs every other player out: each is saved in its own transaction (`guardedLeave`, so a publish that then fails keeps their saves) and then disconnected with `TEXT.publishing` (`deps.kick`). A save that fails stops it there: that player is disconnected with `TEXT.serverError`, nothing is published, and the admin's `contentResult` names whose save failed. Otherwise the publish runs as an ordinary intent. `login`, `create` and `refusal` (a resume) answer `TEXT.publishing` while the lock is held, and `enter` returns false (the gateway reaches it only after one of those), and it is released in a `finally`. The publish runs synchronously on the game thread, so the lock never outlives it and a restart starts unlocked. The count goes to `ContentService.publish` (`loggedOut`), which stores it beside the cleanup in `content_publishes.cleanup` (kept apart from the world's cleanup lines, which Undo's warning is about; the history view's `loggedOut`) and writes the audit entry's `after` as `{ rows, loggedOut }`. The overview's removals carry `inWorld` (the places in the world that hold each), which the confirmation uses to suggest the box. The game lays the NPC editor's saves over the new store's NPC files and sends every player `content` with the new hash. Undo writes the before states back as a publish of its own, refused if any row changed since or a later publish touched it (a later publish and its undo cancel out); undo and accepting a pack notice run every publish check on the store the write would leave (built by doing the write in a transaction that is rolled back). After a publish the game also puts each rebound special body on the online players who wear it (a rider's new body, the tree's or smoke's new one or none, ending a morph that is now one of those; a failed publish puts the old ones back), lays out loaded maps' walk grids again, re-resolves the settings (whose Assassin prize default comes from content), puts online characters' skills in the new order by key (a dropped skill's value is saved for its return, an added one takes its saved value or 1) and resends their sheets, starts again the shop of any NPC whose file changed (its ledger, saved shop and open windows), and sends every player their inventory and the ground items around them again. A pack row whose hash differs from an operator row's base shows as a pack notice: accepting drops the operator row (a publish), dismissing moves its base to the pack row as it is now.

Removing content in use (issue #28). `contentUsage` reports where an item or a monster is used: the references content holds (`referencesOf` in `content/validate.ts` records each reference's row, its JSON path and the entry a cleanup may drop, or none when the entry cannot go without breaking its row, such as a station's one tool or a quest pool's roll) and the world's places (`ContentWorld.usage`, implemented by `createContentWorld` in `systems/admin/content-world.ts`: online players, loaded maps and containers from memory, everyone and everything else from the database, matching stored names with `storedCopyOf`, which knows the `#id`, count and `+N` forms; an item's spellings are its key and archived spellings). The NPC Editor's saves are checked and cleaned as their content rows are (`npcSavesAfter`: the waiting actions' cleanup is applied before the checks and written at publish); player shops' files, in the same `npc_files` table, are world data: never checked as content, their stock counted as copies (usage place `shop`) and purged or replaced with them (rewritten from `liveNpcText`, with a new ledger). A cleanup that would break a row's schema leaves those references instead (`cleanUses`' `rowOk`). `contentRemove` (`ContentService.draftRemoval`) puts the removal in the draft with its cleanup: the content rows the cleanup changes (`cleanUses`: remove the entries, replace the name, or leave them) become ordinary draft rows, and the world's part waits in `content_draft_actions` (migration 55). An item is retired by default (its row gains `"retired": true`; whether anybody still holds a copy is settled at publish, and one nobody holds is removed instead: copies stay and work, `/drop` and the character editor refuse it, and every reference to it counts as unresolved); purge deletes every copy (online, offline, vaults, containers, the ground) with an optional gold refund per copy a character held; replace rewrites every copy. A monster's roster slots are cleared or replaced, live ones despawn (`mgone`) or stay, and its NPC file goes with it or stays. Quest lines naming a removed item are rolled again, or name the replacement; quest lines naming a removed NPC are flagged for review, not checked (1.6's quests name NPCs by their spoken name). The overview's `removals` say what the publish will do; the publish runs the waiting actions once the new store is live, in the same transaction as the content rows (`ContentWorld.begin` snapshots memory before the transaction and from then holds every client message, the new store's `content`, `inv`, ground and closed windows included, until `commit`; if the publish throws, the store that was live goes back, then `ContentWorld.rollback` puts memory back from the snapshot, shop ledgers and open shop windows included, and drops what was held), writes the touched players, containers, ground and quest lines at once (`flushChanged`), moves a replaced container's storage to its new name (wherever the copy is, a vault included, though deposits never put one there) (a container is only replaced with another, under a freshly minted `#id`, so it never lands on another container's storage) or deletes it with a purged one, moves a replaced crystal pile's count to its quantity, records the lines in `content_publishes.cleanup`, and logs each change to a character as an `admin` activity event, so the ledger check finds nothing unlogged. Undo puts the content rows back but not the world. `contentProblems` lists references nothing resolves: content's (`brokenReferences`) and the world's (`ContentWorld.problems`: stored items no catalogue has, roster species no monster list has). They never crash the game (an unknown item shows by its name with no picture; an unknown species spawns as a stand-in with the Generic body and 1 HP), and the server logs the world's at start. `packages/server/tests/content-removal-sweep.test.ts` checks these invariants for every Classic item and monster with every cleanup option (`bun run test:sweep`; `bun run test` runs a seeded sample).

The gateway serves the published store, and the last few before it (so a client that asked just before a publish still gets one), at `/content/<hash>.json` (gzipped when asked, cached as immutable) and its hash at `/content/current.json`, and `welcome` carries the hash. Each installed pack's art and sounds are served under `/assets/packs/<id>/` and merged into `/assets/index.json` (`mergePackArt` in the gateway); a pack that is not installed sends none. Ground items (`GroundView.sprite`) and the inventory (`InventoryView.sprites`) carry an item's sprite key whenever it differs from its key, and the client draws by it.

### The player hub

The Characters page (`characterView`) sends `characterSearch`: characters whose name contains the text, ignoring case, those starting with it first, then the most recently saved, at most `CHARACTER_SEARCH_LIMIT` (`searchCharacters`). Who is online, and an online character's level and class, come from the world. A row sends `characterOpen`, and [`characterHub`](../../packages/server/src/systems/admin/characters.ts) answers with the hub: an online character's sheet is read from the live `Player` (`liveSheet`), since what is saved can be a save interval behind; an offline one from the database (`loadStoredCharacter`, `storedSheet`). Both build the same `CharacterSheet`, and a test pins that a character reads the same before and after logging out; the live gold is the saved purse (`savedGold`), so a blackjack stake held at the table does not make it jump when the player drops mid-hand. The hub also carries the ban, jail and mute in force and the newest `HUB_HISTORY` moderation entries; the newest `HUB_CHAT_LINES` chat lines only for a role with `chatlog`; and only for one with `banip`, as on `/banlist`, the login addresses, the IP bans in force on them (`ipBansOn`, one per banned key, since a ban made by address alone has no history row) and whether the character's role bypasses IP bans. Without `banip` an IP ban's history row comes with its address removed. Every hub read is written to the audit log as `characterView`, noting whether it held the chat and the addresses.

The hub's moderation buttons send `characterModerate` with a length and a reason. The server checks the command's own permission (a role without it is cheat-logged), refuses a ban, jail or mute with no reason, reads the length with `hubArgs` (empty means the setting's default) and runs `moderate` in commands.ts, the same code as `/kick`, `/ban`, `/unban`, `/jail`, `/unjail`, `/mute` and `/unmute`, with their rank checks, moderation log and audit. A kick takes no reason, as `/kick` logs none; it answers with the typed command's echo, and kicking yourself is refused, since it would end the session the hub answers. The lines the command would have printed come back as `characterResult` with the request's `seq`; it counts as done when the command wrote its audit row. A role without the command's permission also gets a refusal, so a hub whose role changed is not left waiting. The client applies a result only to the hub that asked, then reads it again. When your permissions change, the open hub drops the chat and addresses you may no longer read, an open question closes, and the hub is read again; a question is also closed when you leave the page or open another character, and is checked again before it is sent.

### The character editor

The hub's Edit tab (`characterEditor`) sends `characterEdit`: `set`, the new values of the fields that changed, and `seen`, what the hub showed for them, with a reason and the wear-rule override. Edits never go straight to the database. [`prepareEdit`](../../packages/server/src/systems/admin/character-edit.ts) reads the character as the hub does (`liveSheet` or `storedSheet`, flattened by `editableOf`), refuses the edit when a `seen` value no longer matches (a stale hub), applies `set` with `deriveEdit` (a level change sets `expNeeded` with `expNeededAt` and moves `hpMax` and `spMax` by the level difference; HP, SP and experience not typed come within their new limits) and checks the result with `editErrors` (hard limits; only fields that changed are checked item by item, so an old item in a bag does not block an unrelated edit) and `wearBreaks` (slot, strength with class and medal points, two-handed weapons and murder gear; only slots the edit changed). The stale check covers `staleCheckFields`: the fields set, plus experience, HP and SP when the level changes, since `deriveEdit` may bring them within new limits. `storageIdErrors` refuses an `#id` item the character did not already hold, or more copies of one than they held (a stack counts each unit), so a Crate's storage is never shared; an `#id` item never stacks and can't be worn. A name the character already holds may move between lines even when the catalogue no longer lists it (a painting, a retired item). Gold, in any spelling, is not a bag or vault item, and the vault refuses containers as a deposit does. `wearBreaks` leaves gear already worn alone, except that clearing the wanted flag re-checks murder gear. `placeChecks` resolves map names, refuses gold, item and position fields while the target trades or holds a casino seat (seats are found by character id, so a player who dropped mid-hand still counts), refuses a move while they are jailed or in an editor, and keeps non-staff off the jail map. A bare Crate, Cabinet or Cauldron gets its own `#id`, as `invAdd` gives one.

`applyEdit` in game.ts runs in the intent's transaction. It first runs the target's ledger check (`logEdit` "before"), so anything play had not logged is reported as play's. It then changes the live `Player` (`applyLive`: vitals, inventory, spellbook, an open vault's list and sheet messages; a `look` delta carrying the new head; `adminWarp` for a move) and saves them at once (`save`, `saveLookAndClass`, `persistItems`), or for an offline character rewrites the saved rows (`writeOffline`). A move keeps the respawn point the edit shows, even onto an O-O-O map that would set one on arrival, so a move or its undo never changes it on the side and online and offline edits end alike; the changes are then read back from the live character, so the log holds what the character ended as. A new head goes to everyone on the map as a `look` event with `head` (only to the admin themselves while they are off the map), an open vault is redrawn and a crate or cabinet opened from the bag closes when the edit takes it away. If a write throws, the target is kicked and taken off the map as the acting player is, since their memory changed but the database rolled back. Then come the `character_edits` row (reason and `changes`, each field's `before` and `after`), the audit row and the activity events: the gold and items moved as `admin` events from the admin, bank and vault changes as `admin` events with their amounts in `details`, and one `admin` event naming the other fields. The online ledger then starts again, so the next check finds nothing `unlogged`.

`characterUndo` (`prepareUndo`) applies an edit's `before` values only while every field it changed still holds its `after` value (`undoConflicts`); otherwise it names the fields that moved. The restored state must still hold together (`editErrors` with `restore`: experience, HP and SP within their limits), and gear it puts back must pass `wearBreaks`, since an undo never carries an override. The client sends one change at a time, so a second cannot hide the first one's answer. An undo is an edit of its own, with `undo_of`, and marks the original's `undone_by`, so an edit is undone once. Results come back as `characterResult` with the request's `seq`, as the moderation buttons' do. A house revoke or transfer row (`kind` other than `edit`) is refused with `EDIT_TEXT.noUndoHouse`.

#### Houses in the hub

Issue #36. The hub carries `houses`, one [`HubHouse`](../../packages/shared/src/rules/admin/characters.ts) per house the character owns (`hubHouses` in [house-admin.ts](../../packages/server/src/systems/admin/house-admin.ts)): the interior, the outdoor map and the exit's tile, the type (`houseTypeOf`: the blueprint does not name it, so it is matched by its tile codes and offsets and what stands outside, a mailbox, the Street Lamp or nothing), each player shop in the interior (its SEL lines, its stock and its till, read through the ledger) and the owner's House Vault count.

`characterHousePreview` (`characterView`) answers with a `HousePreview` from `housePreview`, or the reason there is none: the vault and its fate (a revoke `destroyed` with the owner's last house, else `kept`; a transfer `kept` while the old owner keeps another house, else `moved` or `merged` into the new owner's), each shop's stock and till, the counted items on the interior's floor and who stands inside. A transfer is refused there before anything changes: the target must be another existing character, a guild hall's must belong to the guild its fixtures name (`hallGuild`), and a merge must fit `containerCapacity`. `expect` hashes the preview; `characterHouseRevoke` and `characterHouseTransfer` (`characterEditor`, a reason required) build it again and refuse with `HOUSE_ADMIN_TEXT.changed` when it no longer matches.

A revoke (`characterHouseRevoke` in game.ts) moves everyone inside to the tile below the house's exit (`moveOut`: `warp` with `via: "houseRevoke"`; someone in the Control Panel over the interior is placed there without leaving it), clears live respawn points inside it, runs `demolish`, takes the house's entries off `houseList`, writes the houses and ground, and deletes the interior at once (`flushInteriorDeletes`), so its floor, shops and (with the owner's last house) vault are logged as `demolish` world events. `demolish` keeps the House Vault while the owner still owns a house (`ownsAHouse`), for decay too.

A transfer (`transferHouse`) renames the old owner's fixtures, `<owner>'s Door`, `<owner>'s Opened Door`, the interior's `<owner>'s House Vault` and the blueprint's mailbox, with `gset` deltas and ground-log writes; renames the interior's header and Sign 3 when they name the owner (`saveMapTitleAndSigns`); moves the blueprint and its list entries (whose month restarts) to the new owner; and points each shop in the interior at them (`player_shops.owner_id`, `setPlayerShopOwner`). The blueprint's mailbox is matched by name and tile, so another house of the old owner's on the same map keeps its own. The shopkeepers' `OWN|` line is rewritten in place (`withShopOwner`), leaving the ledger. Every ownership check reads those names and ids (door keys, `mayUseContainer`, the shop's register and stock commands, `title`, the do-not-drop flag, which in a personal house's interior is the blueprint owner's (`dropFlag`, `houseDrop`), the mailbox, decay), so the old owner's rights end at once; a House Vault window open in the interior and a session at the transferred mailbox (`mailBox`) close.

Both run through `houseChange`: what they send waits in `afterCommit` until the intent's transaction commits, and if a write throws, `houseSnapshot` puts the memory back (blueprints, list, pending ground and tile writes, the two maps, the vaults, the shops and their files) and anyone a revoke moved is kicked to reload from the database. A revoke saves the evacuees' positions and the purses of anyone at a casino table before the interior is deleted, so a restart keeps them outside, and refuses when the outdoor map is missing (`HOUSE_ADMIN_TEXT.noMap`), since `demolish` would do nothing. The rollback runs from the intent's own catch (`rollbacks`), so a failure after the change, such as writing its activity, restores memory too; it also restores the containers waiting to be written, the casino tables, every player's open windows and sessions, and the deleted interior's cached map and room.

Deleting an interior (`deleteInterior`, for decay too) closes its casino tables (`closeTablesOn`: each stake still held is refunded as `refundHolds` does at shutdown, and a seat kept for a player away in the reconnect grace goes, so `bjReturn` finds nothing), closes shop and Bio windows on its shopkeepers (`closeNpcWindows`) and clears live respawn points inside. `demolish` and a transfer end a session at the house's mailbox with `closeMailAt`, which sends `mailClosed`; `mailBox` records where a session was opened and clears with it and on a room change. A preview's `renames` and `guild` tailor the confirmation and the new owner's message to a house, a Small Shop or a guild hall. The floor list sums piles as they count (`countedPile`). The preview's `expect` also hashes the interior's map id, so a house demolished and built again the same is a different house. A vault moved with the owner's last house is logged as world `container` rows (a move: reconciliation does not count it), and any open window on either vault closes. Both owners are told if online.

Each writes `character_edits` rows (migration 72 added `kind`, `summary` and `irreversible`): a revoke on the owner's history, irreversible; a transfer on both characters'. The summary (`previewSummary`) names what was destroyed or moved. The audit log gets `houseRevoke` or `houseTransfer`.

### The activity log

Every system that moves a player's items or gold, or decides a kill, a death or a map change, appends one event with [`logActivity`](../../packages/server/src/systems/admin/activity.ts) at the point it decides it. An event is one character's view: `qty` and `gold` are signed changes to what that character carries (bag, worn gear and gold in hand), so a trade or give writes a row for each side and a bank deposit is negative. `other` names the other party; a player also gets their id, so the Control Panel can link their timeline. Things put on the ground but never carried (monster loot, a gathered find, an admin's `/drop`) are logged with `qty` 0 and `details.placed` (`logPlaced`). A whole-bag change (a shop sale, a craft) is logged as the difference before and after (`logBagChange`). Ground items remember who dropped or gave them (`droppedBy`, stored with the item), so a pickup names them. A character who is not online (an offline blackjack winner, an Assassin prize sent to their bag) is logged without a place. A world event that makes or destroys items with no player behind it is logged with no character (`logWorld`, `logWorldLines`; migration 71 made `account_id`, `character_id` and `character` nullable): `decay` for ground items whose time ran out (`decayLoot` on a loaded map, and `groundFor` for the rows `loadGround` deletes when a map loads), `refill` for a quest chest's line (`saveClockStep`), `demolish` for a demolished house's outdoor items and, with the owner's last house, vault (`demolish`) and its interior's floor and shops' stock and till (`deleteInterior`, after `flushInteriorDeletes` has written the waiting ground changes), and `regrow` for regrowth's produce. Their `qty` and `gold` are the change to what exists. A content publish that purges or replaces an item logs its containers, ground and player-shop copies as world `admin` events too, and its vault changes one row per name.

Each player keeps a ledger of what the log says they carry (`activityHeld`), started at login after a blackjack seat is restored. Each logged change moves it. Once a tick, and when they leave, `checkPlayer` compares it with the bag, worn gear and gold. A difference is written as `unlogged`, so a source or sink no system logged, or a dupe, still shows up. The same check compares levels, class and skills with the last ones seen and logs what went up, since skills rise in many places. Map changes are logged by `warp` with how they happened (`via`).

A new character's starting items are logged as `reward` when it is created, and a map save from the World page logs the net change in the map's placed items for the admin who saved it (`logEditorPlacements`). A kill by a spell whose caster has left the map, or by a player who has logged off, is still credited to them by id.

Events collect in `world.activity` and are written (`flushActivity`) at the end of the transaction of the intent, login, logout, tick or character creation that logged them, while chat lines still wait for the next tick, so an item change and its row always commit together (the item reconciliation relies on it); they are stamped with the time their intent ended. The once-a-tick ledger check's `unlogged` rows, logged after the tick's transaction, are written with the next one. Buffered rows leave memory only once the transaction that wrote them commits (`commitLogs`); a rollback keeps them to be written again (`rollbackLogs`), and shutdown writes the last logouts after the sockets close (`flushLogs`). A restart forgets the blackjack tables, so before the final save a clean shutdown pays back every stake still held and logs it as a `casino` refund (`refundHolds`): into the purse of a seated player, or only as a row for one away in the reconnect grace, whose saved purse already holds it. A crash skips this, so `persistItems` keeps the stakes held in `casino_holds`, written with the purses that count them, and the next start logs each one left there as a `reward` refund (`restart: true`) and empties the table. The once-a-tick holdings check runs after the tick's transaction, since it writes no SQL. When an intent, login or logout throws, its SQL rolls back and the player is evicted to reload from the database, so their events from that call are dropped, with any world event it logged (`dropActivity`); other players' events stay, since their memory, which is what gets saved, did change. The Activity Log page sends `activityQuery` (gated by `activityLog` in `ADMIN_INTENTS`, and taken in the Control Panel through `EDITOR_INTENTS`). The answer is a page of rows newest first, paged by the last row's time and id. The first page of an item's flow also carries totals by type, over at most the newest `ACTIVITY_TOTALS_MAX` events (the query runs on the game's thread; `totalsCapped` says when older ones were left out). Every read, each page included, is written to the audit log as `activityLog`. `activityLogRetention` prunes the table hourly, but never a row after the last reconciliation run's `last_seq` (`pruneActivity`'s `keepAfterSeq`), so the next run always reads every row since the last. The item flow of the currency's name reads every row whose gold changes (`gold`, `placedGold`, `bank`; scope `{ gold: true }`).

#### Item reconciliation

Issue #35. Each activity type is classed in `ACTIVITY_COUNTS` ([reconcile.ts](../../packages/shared/src/rules/admin/reconcile.ts)): a **move** changes where an item is (`trade`, `give`, `drop`, `pickup`, `playerShop`, `bank`, `vault`, `container`, `deathDrop`); a **make** counts its signed `qty` and `gold` (`buy`, `sell`, `reward`, `pay`, `use`, `spell`, `loot`, `gather`, `craft`, `transform`, `quest`, `casino`, `admin` and the world events); `unlogged` is kept apart. Whatever the type, `activityChange` adds a row's details: `placed`/`placedGold` (made on the ground: loot, gathering, a faction head, `/drop`, a vehicle built from its deed, a house's built-in items), `stored` (made or used up in a container: a Cauldron's brew, logged as `craft`), `vault` and `bank` (an admin's change there), and subtracts `lost` (a pickup into a full bag, an item sold to a player shop with no line to stock it, a vehicle lost at a death as `deathDrop`). A row with `as: "monster"` (a Pig grabbed or let go) counts its `qty` though it is a pickup or drop. Gold given to a player's shopkeeper is a `playerShop` move into its counted till (`till`, `gift`); given to any other NPC it is a `pay`. A Newspaper Kit put down as a stand is a `use` (the stand, `<owner>'s Newspaper`, is an owned fixture `countedPile` does not count, as content-world.ts's `OWNED_FIXTURE` treats it). `lost` counts only on a move: on a make (an Assassin prize with no room in the bag) it is an item never made. `countedPile` says what a stored name counts as: a currency pile is gold, a crystal pile its count, a parked vehicle (`Bob's Airship`) or a character's `vehicle` one of its kind, a container without its `#id`; engine fixtures and `isDoorOrSwitch` names are not counted.

`runReconcile` in game.ts runs inside the intent's or tick's transaction: it runs every online player's ledger check (`checkHoldings`), saves everything as `/save` does (`saveEveryone`), then `countHoldings` reads every holder (inventory slots 1 to 15, equipment, character gold and vehicle, bank balances, vault and container lines, every ground row, player shops' saved ledger or file, less `casino_holds`), `activityFlows` sums the rows after the last run's `last_seq` in SQL, by type, item and the signs of their changes (`activityChange` is linear, so it works on the sums), and every holder is grouped by item in SQL, so only one line per item reaches the game thread (`activity_log.seq` is an AUTOINCREMENT key added by migration 71, so it only grows), and `reconcileItems` makes each item's line: baseline (the last run's actual), made, ended, unlogged, expected, actual and difference. The first run stores only the baseline. `insertRun` writes `reconcile_runs` and `reconcile_items` and keeps the newest `RECONCILE_RUNS_KEPT`. The Activity Log page's Reconciliation view sends `reconcileQuery` (the newest `RECONCILE_RUNS_SHOWN` runs, each with its flagged lines, at most `RECONCILE_ROWS_MAX`) and `reconcileRun` (a run now, audited as `reconcile`), both gated by `activityLog` in `ADMIN_INTENTS` and listed in `EDITOR_INTENTS`. With `GameDeps.nightlyReconcile` (main.ts sets it), the tick checks once a minute and runs when no run has happened since the latest `RECONCILE_NIGHTLY_HOUR` (04:00 UTC), in its own transaction after the tick's, so a run that fails rolls back only itself and is tried again a minute later (the last run's time is read from `reconcile_runs`, so a run that rolled back never counts as done). `playerShopStock` reads the shops in three joined queries on exact names.

A roster reports map contents; spawn and drop requests validate their names and amounts. The World page and the NPC file editor are restricted and validate submitted data before saving it. The World page (issue #33, which replaced the frame-262 World Editor) sends `contentMaps`, `contentMapSave` and `contentMapRestore`, gated by `contentEditor`; a save goes through the same checks and live apply the World Editor's SAVE did (`saveError`, `applySave`, `map_versions`, the `editSave` audit line) and names the map's revision. World editor saves apply to the server's map state; NPC edits check the file and refresh windows that display the edited NPC. Read paths expose information without giving the reader permission to edit it. The historical monster-drop editor and Justicars are not revived.

### Permissions, tools and persistence

By default moderators and administrators share the moderation commands (`/kick`, `/ban`, `/unban`, `/jail`, `/unjail`, `/mute`, `/unmute`, `/banlist`, `/Location` and `/Inventory`), and all staff can post to and read `-text` staff chat. A moderator is an ordinary player who moderates others: the warps (`/warp`, `/warptome`, `/warpmeto`, `/warpscript`) are administrators', and only an administrator may pardon or warp themselves (`pardonSelf`, `warpSelf`). `/pardon`, `/IPlookup`, `/save`, `/Refresh`, IP bans (`/BanIP` and `/unbanip`), `/chatlog`, `/auditlog`, `/CheatFile` (audited on each use), `/drop`, `/setclass`, `/roster`, `/spawn`, and the World Editor, NPC Editor, and the Control Panel with its Server Settings page are administrators' too. A command anyone lacks the permission for is answered as an unknown command. `/kick`, `/IPlookup`, `/warp` and `/warptome` refuse a target who outranks the staff member, so staff of equal rank can still kick or look up each other; `/pardon`, like the bans, jails and mutes below, needs the staff member to outrank the target (`mayTarget`). `/warpscript` never warps a speaker who outranks the staff member. Commands use the account's role as it stands, and administrative actions use [admin persistence](../../packages/server/src/persistence/admin.ts) for account lookups and audit rows. A missing target or jail map is reported rather than silently trusting a supplied destination.

### Bans, jails and IP bans

`/ban`, `/jail`, `/mute` and `/banip` take an optional duration and reason after the name. Durations such as `30m`, `7d` and `perm` are parsed by `parseModerationArgs`; a missing one uses the `banLength`, `jailSentence`, `muteLength` or `ipBanLength` setting. Every staff action is written to the moderation log with the staff member's name and the name of their role at that moment, and the bans, IP bans, jails and mutes in force are kept in their own tables until they end. A ban, IP ban, jail sentence or mute that runs out by itself is logged as ended by `system` (reason "Expired", dated when it ended), by `expireModeration` once a minute and at startup. `/banlist` pages its bans 10 at a time and lists the first 10 jails and mutes; IP bans and addresses appear only for a role with `/banip`. Staff can ban, jail, mute or pardon only those they outrank, and a role with `overrule` (administrators) can act on anyone but themselves (`mayTarget`). Only the staff member who made a ban, jail or mute, or a role with `overrule`, can change its length or lift it (`mayChange`), so a moderator can no longer overwrite an administrator's ban to lift it.

`/chatlog <name> [count] [channel]` prints a character's newest logged chat (see the [Chat guide](chat.md#the-chat-log)), including the IMs sent to them. It needs the `chatlog` permission (anyone else is told it is an unknown command), it covers every channel, and each lookup is audited.

`/auditlog <name> [count]` prints the newest staff actions (default 10, up to 100) taken by that character's account or done to that character. [`auditTrail`](../../packages/server/src/persistence/admin.ts) merges the audit log with the moderation log, which supplies bans, jails, mutes, IP bans, unmutes and pardons with their reasons, and leaves out the audit log's copy of those. It needs the `auditlog` permission, and each lookup is audited.

A jailed or muted player is told in the chat box until when, at once and at each login. Every way of talking (local chat, `/me`, broadcasts, IMs, guild chat, rooms, staff chat, mail and boards) asks [`silenced`](../../packages/server/src/systems/chat/speech.ts) first: a muted player says nothing, a prisoner is heard only on the jail map (a jailed staff member keeps staff chat, which reaches only staff), and either may still IM staff. A mute also refuses player-shop commands, which are typed into chat; a prisoner can still run them. `chatWait` and `broadcastWait` in the same file let a role with the bypass permissions skip the chat and broadcast cooldowns. A mute is on the account, runs in real time and is lifted by `muteTick` when it ends. A banned player reads the alert and the ban's end at login; the reason is shown only to staff, through `/banlist`. An account ban and an IP ban are checked after the password, and IP bans never stop a role with `bypassIpBan`. An IPv6 address bans its /64. The server records the addresses each account logs in from, so `/banip <name>` can ban the latest or every one, and a new IP ban disconnects matching sessions immediately. A jail sentence is stored and runs in real time. An offline prisoner is placed in jail at login, and one whose sentence ended while away goes to their respawn point (the fallback point if its map is gone). `/warp` refuses a map that does not exist. Staff warps cannot move a prisoner out of jail or a player into it.

Staff chat (`-text`) uses a dedicated colour (`CHAT_COLOR.staff`), has no house sender restriction, muffling, or ignore filtering, and reaches only staff recipients. A muted staff member cannot post to it. `-text` from a non-staff player gets "Only staff can use staff chat." and the input clears; `/warpscript` from anyone without the permission is an unknown command, and the line returns to the input. `/warpscript` matches whole keywords in broadcast message content only (ignoring case, never matching speaker names, protocol wrappers, or substrings) and warps the speaker to the first matching online staff member in login order, skipping staff who are in an editor, ignore the speaker or are outranked by them, and, for a speaker who is not staff, staff on the jail map.

Login attempts are counted over five minutes and account creations over an hour; a zero setting disables the corresponding limit. The counts are in memory and reset on restart. A successful password removes that attempt and clears the account-and-address count. A role with `bypassLoginLimits` is not stopped by an address that has used up its count, but only while its account has no failure from that address in the window, so a spent address gets one try at a staff password, not a run of guesses. The roster command sets one of four map slots; spawn places a rostered creature immediately on the faced tile. The drop command accepts a recognised item, with a count of up to 9,999 for a stack (`DROP_MAX`), or any positive amount of gold, and puts the pile on the faced tile.

A staff member entering an editor leaves the map until returning. A world save checks map fields, exits, text and item names, replaces its editor-managed items and roster, and refreshes players on the map; other ground drops and loot are preserved. The Fat brush paints a plus of five tiles, clipped at the map's edges, the faction boxes (W/M/A in Classic, each picking a faction by key) are mutually exclusive, clicking a lit layer button (including S) keeps that layer selected, and loading a map without an exit resets the exit fields. NPC loading combines the file with live shop stock and gold and displays the complete text losslessly. Saving validates the selected NPC and its lines, replaces its file and resets its shop ledger; open shop and bio windows for it close. The editor lists and validations are in the shared files listed above.
