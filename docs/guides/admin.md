# Admin

## What happens in play

Staff hold a role that the operator defines: by default a moderator can kick, ban, jail and mute players, while an administrator can also warp, edit the world and change the server's settings and roles. The server checks the role's permissions before it acts.

## How it works

The server routes administration requests through `handleAdmin` and checks permissions using `can`. Commands also record audit information. Login limits track attempts by IP and account and limit character creation.

### Roles

A role has an id, a display name, a rank and a set of permissions: one per admin command and tool, plus the gameplay exemptions (takes no damage, never hungry, cannot be pushed, off the high scores, not stopped by IP bans or login limits, drops on every death, and skips the chat or broadcast cooldown). The operator's roles live in the database's `roles` table; a new server starts with `moderator` (Moderator, rank 1) and `administrator` (Admin, rank 2). An account holds at most one role, and an account with none is an ordinary player: rank 0, no permissions. Any role makes an account staff, so it reads and posts staff chat and can be sent IMs by jailed and muted players. Nothing checks a role by name. The client receives only its permissions, to decide which menus to show, and the server checks every request.

Roles are edited on the Server Settings page's Roles page and given to accounts on its Staff page, both gated by the `settings` permission, or with `bun run admin:role <name> <role|none>` (and `--list`). There is no in-game command for it. A change made in Server Settings applies at once to everyone online who holds the role: they get their new permissions, a `/warpscript` they may no longer use is cleared and an editor or the Control Panel they may no longer use closes (`applyRole`, `mayEdit`), and on the next tick they leave a room such as Admin Chat they may no longer use (`roomMembership`). A change made with `bun run admin:role` takes effect at the account's next login. Deleting a role leaves its accounts with no role. At least one role must keep every permission (`rolesError`), and nobody can change their own role on the Staff page, so the server can always be run; the command line can always give a role. Every role edit, deletion and assignment is written to the audit log.

The Chat page's Role tags setting (off by default) puts the speaker's role name before their name in local chat, `/me`, broadcasts, chat rooms, guild chat and staff chat: `[Admin] Berlyn says "hi"` (`taggedName`). IMs keep the plain name, since it is the address a reply goes to, and ignore lists still match the plain name.

### The Control Panel

The Control Panel is a full-page dashboard in the client, opened from **Admin → Control Panel** by a role holding a permission in `CONTROL_PANEL_PERMISSIONS` (today `settings`, `characterView`, `activityLog` and `contentEditor`; each Control Panel page adds its own). The server checks it again (`canOpenControlPanel`) and writes a refused `controlPanelOpen` to the cheat log. Opening it works like the World Editor: `openControlPanel` calls `leaveForEditor` with `"controlPanel"`, so the admin stays online but leaves the map (everyone there sees them go, trades, shops and held actions are cancelled, nothing on it ticks for them). Return to Game sends `editClose`, and `closeEditor` puts them back where they stood with the login i-frames. Moving between the Control Panel and the World or NPC Editor only changes `editing`, so the admin never reappears on the map in between. While in the Control Panel the server takes only `EDITOR_INTENTS`: the editors', the Control Panel's pages' and the floating windows' (IM, Away, chat rooms, Friends, Bio, Who's Online and Player Settings).

In the client the Control Panel replaces the game view and its classic menu bar. Its header has Return to Game, the floating-window tools (with a count of IMs that arrived while it is open) and Return To Title Screen; its sidebar lists the pages your role may use, then the classic editors. The floating windows use their own size over the Control Panel instead of the 800×600 frame's scale. A page reports its unsaved changes, and leaving it asks first. Each page's own requests are still gated by their permission on the server (`ADMIN_INTENTS`). `characterEditor` gates the hub's editor; `contentEditor` gates the Content page.

### The content store

Every rule reaches content through the shared content store (`content()` in `packages/shared/src/content/store.ts`). The server's `ContentService` (`packages/server/src/content/service.ts`) builds it at start-up from the installed packs (`content_packs`; Classic is read from `packages/data/packs/classic/` in the release) and the operator layer (`content_rows`), and installs it before the game loads. A dataset's top-level field is either a keyed list, whose entries are rows by key (`KEYED_LISTS` in `content/rows.ts`: items and monsters by name, NPC files, spells, help topics, classes, skills, deeds, house types, factions), or one row of its own. Operator rows never edit pack rows in place: a change, an addition or a removal marker sits on top, with the hash and JSON of the pack row it was based on.

The Content page's intents (`contentOverview`, `contentList`, `contentRow`, `contentDraft`, `contentDiscard`, `contentPublish`, `contentUndo`, `contentNotice`; `content/page.ts`) need `contentEditor`. A draft change must keep its dataset valid against its schema; a publish runs every check (`content/validate.ts`: schemas, then the key and name rules, then the references a change breaks, compared with the published store so Classic's own unresolved names are not reported), refuses a draft another admin changed since it was read, writes the operator rows, the publish log (`content_publishes`, each row's state before and after) and an audit entry in one transaction, then swaps the store in. The game lays the NPC editor's saves over the new store's NPC files and sends every player `content` with the new hash. Undo writes the before states back as a publish of its own, refused if any row changed since. A pack row whose hash differs from an operator row's base shows as a pack notice: accepting drops the operator row (a publish), dismissing moves its base to the pack row as it is now.

The gateway serves the published store at `/content/<hash>.json` (gzipped when asked, cached as immutable) and its hash at `/content/current.json`, and `welcome` carries the hash. The release's atlases are served only while Classic is installed.

### The player hub

The Characters page (`characterView`) sends `characterSearch`: characters whose name contains the text, ignoring case, those starting with it first, then the most recently saved, at most `CHARACTER_SEARCH_LIMIT` (`searchCharacters`). Who is online, and an online character's level and class, come from the world. A row sends `characterOpen`, and [`characterHub`](../../packages/server/src/systems/admin/characters.ts) answers with the hub: an online character's sheet is read from the live `Player` (`liveSheet`), since what is saved can be a save interval behind; an offline one from the database (`loadStoredCharacter`, `storedSheet`). Both build the same `CharacterSheet`, and a test pins that a character reads the same before and after logging out; the live gold is the saved purse (`savedGold`), so a blackjack stake held at the table does not make it jump when the player drops mid-hand. The hub also carries the ban, jail and mute in force and the newest `HUB_HISTORY` moderation entries; the newest `HUB_CHAT_LINES` chat lines only for a role with `chatlog`; and only for one with `banip`, as on `/banlist`, the login addresses, the IP bans in force on them (`ipBansOn`, one per banned key, since a ban made by address alone has no history row) and whether the character's role bypasses IP bans. Without `banip` an IP ban's history row comes with its address removed. Every hub read is written to the audit log as `characterView`, noting whether it held the chat and the addresses.

The hub's moderation buttons send `characterModerate` with a length and a reason. The server checks the command's own permission (a role without it is cheat-logged), refuses a ban, jail or mute with no reason, reads the length with `hubArgs` (empty means the setting's default) and runs `moderate` in commands.ts, the same code as `/kick`, `/ban`, `/unban`, `/jail`, `/unjail`, `/mute` and `/unmute`, with their rank checks, moderation log and audit. A kick takes no reason, as `/kick` logs none; it answers with the typed command's echo, and kicking yourself is refused, since it would end the session the hub answers. The lines the command would have printed come back as `characterResult` with the request's `seq`; it counts as done when the command wrote its audit row. A role without the command's permission also gets a refusal, so a hub whose role changed is not left waiting. The client applies a result only to the hub that asked, then reads it again. When your permissions change, the open hub drops the chat and addresses you may no longer read, an open question closes, and the hub is read again; a question is also closed when you leave the page or open another character, and is checked again before it is sent.

### The character editor

The hub's Edit tab (`characterEditor`) sends `characterEdit`: `set`, the new values of the fields that changed, and `seen`, what the hub showed for them, with a reason and the wear-rule override. Edits never go straight to the database. [`prepareEdit`](../../packages/server/src/systems/admin/character-edit.ts) reads the character as the hub does (`liveSheet` or `storedSheet`, flattened by `editableOf`), refuses the edit when a `seen` value no longer matches (a stale hub), applies `set` with `deriveEdit` (a level change sets `expNeeded` with `expNeededAt` and moves `hpMax` and `spMax` by the level difference; HP, SP and experience not typed come within their new limits) and checks the result with `editErrors` (hard limits; only fields that changed are checked item by item, so an old item in a bag does not block an unrelated edit) and `wearBreaks` (slot, strength with class and medal points, two-handed weapons and murder gear; only slots the edit changed). The stale check covers `staleCheckFields`: the fields set, plus experience, HP and SP when the level changes, since `deriveEdit` may bring them within new limits. `storageIdErrors` refuses an `#id` item the character did not already hold, or more copies of one than they held (a stack counts each unit), so a Crate's storage is never shared; an `#id` item never stacks and can't be worn. A name the character already holds may move between lines even when the catalogue no longer lists it (a painting, a retired item). Gold, in any spelling, is not a bag or vault item, and the vault refuses containers as a deposit does. `wearBreaks` leaves gear already worn alone, except that clearing the wanted flag re-checks murder gear. `placeChecks` resolves map names, refuses gold, item and position fields while the target trades or holds a casino seat (seats are found by character id, so a player who dropped mid-hand still counts), refuses a move while they are jailed or in an editor, and keeps non-staff off the jail map. A bare Crate, Cabinet or Cauldron gets its own `#id`, as `invAdd` gives one.

`applyEdit` in game.ts runs in the intent's transaction. It first runs the target's ledger check (`logEdit` "before"), so anything play had not logged is reported as play's. It then changes the live `Player` (`applyLive`: vitals, inventory, spellbook, an open vault's list and sheet messages; a `look` delta carrying the new head; `adminWarp` for a move) and saves them at once (`save`, `saveLookAndClass`, `persistItems`), or for an offline character rewrites the saved rows (`writeOffline`). A move keeps the respawn point the edit shows, even onto an O-O-O map that would set one on arrival, so a move or its undo never changes it on the side and online and offline edits end alike; the changes are then read back from the live character, so the log holds what the character ended as. A new head goes to everyone on the map as a `look` event with `head` (only to the admin themselves while they are off the map), an open vault is redrawn and a crate or cabinet opened from the bag closes when the edit takes it away. If a write throws, the target is kicked and taken off the map as the acting player is, since their memory changed but the database rolled back. Then come the `character_edits` row (reason and `changes`, each field's `before` and `after`), the audit row and the activity events: the gold and items moved as `admin` events from the admin, bank and vault changes as `admin` events with their amounts in `details`, and one `admin` event naming the other fields. The online ledger then starts again, so the next check finds nothing `unlogged`.

`characterUndo` (`prepareUndo`) applies an edit's `before` values only while every field it changed still holds its `after` value (`undoConflicts`); otherwise it names the fields that moved. The restored state must still hold together (`editErrors` with `restore`: experience, HP and SP within their limits), and gear it puts back must pass `wearBreaks`, since an undo never carries an override. The client sends one change at a time, so a second cannot hide the first one's answer. An undo is an edit of its own, with `undo_of`, and marks the original's `undone_by`, so an edit is undone once. Results come back as `characterResult` with the request's `seq`, as the moderation buttons' do. Houses are not edited here yet (issue #36).

### The activity log

Every system that moves a player's items or gold, or decides a kill, a death or a map change, appends one event with [`logActivity`](../../packages/server/src/systems/admin/activity.ts) at the point it decides it. An event is one character's view: `qty` and `gold` are signed changes to what that character carries (bag, worn gear and gold in hand), so a trade or give writes a row for each side and a bank deposit is negative. `other` names the other party; a player also gets their id, so the Control Panel can link their timeline. Things put on the ground but never carried (monster loot, a gathered find, an admin's `/drop`) are logged with `qty` 0 and `details.placed` (`logPlaced`). A whole-bag change (a shop sale, a craft) is logged as the difference before and after (`logBagChange`). Ground items remember who dropped or gave them (`droppedBy`, stored with the item), so a pickup names them. A character who is not online (an offline blackjack winner, an Assassin prize sent to their bag) is logged without a place.

Each player keeps a ledger of what the log says they carry (`activityHeld`), started at login after a blackjack seat is restored. Each logged change moves it. Once a tick, and when they leave, `checkPlayer` compares it with the bag, worn gear and gold. A difference is written as `unlogged`, so a source or sink no system logged, or a dupe, still shows up. The same check compares levels, class and skills with the last ones seen and logs what went up, since skills rise in many places. Map changes are logged by `warp` with how they happened (`via`).

A new character's starting items are logged as `reward` when it is created, and a World Editor save logs the net change in the map's placed items for the editor (`logEditorPlacements`). A kill by a spell whose caster has left the map, or by a player who has logged off, is still credited to them by id.

Events collect in `world.activity`, are stamped with the time their intent, login or logout ended, and are written with the chat log at the start of the next tick in their own transaction. Buffered rows leave memory only once the transaction that wrote them commits (`commitLogs`); a rollback keeps them to be written again (`rollbackLogs`), and shutdown writes the last logouts after the sockets close (`flushLogs`). A restart forgets the blackjack tables, so before the final save a clean shutdown pays back every stake still held and logs it as a `casino` refund (`refundHolds`): into the purse of a seated player, or only as a row for one away in the reconnect grace, whose saved purse already holds it. A crash skips this, so its stakes come back unlogged. The once-a-tick holdings check runs after the tick's transaction, since it writes no SQL. When an intent, login or logout throws, its SQL rolls back and the player is evicted to reload from the database, so their events from that call are dropped (`dropActivity`); other players' events stay, since their memory, which is what gets saved, did change. The Activity Log page sends `activityQuery` (gated by `activityLog` in `ADMIN_INTENTS`, and taken in the Control Panel through `EDITOR_INTENTS`). The answer is a page of rows newest first, paged by the last row's time and id. The first page of an item's flow also carries totals by type, over at most the newest `ACTIVITY_TOTALS_MAX` events (the query runs on the game's thread; `totalsCapped` says when older ones were left out). Every read, each page included, is written to the audit log as `activityLog`. `activityLogRetention` prunes the table hourly.

A roster reports map contents; spawn and drop requests validate their names and amounts. World and NPC editors are restricted and validate submitted data before saving it. World editor saves apply to the server's map state; NPC edits check the file and refresh windows that display the edited NPC. Read paths expose information without giving the reader permission to edit it. The historical monster-drop editor and Justicars are not revived.

### Permissions, tools and persistence

By default moderators and administrators share the moderation commands (`/kick`, `/ban`, `/unban`, `/jail`, `/unjail`, `/mute`, `/unmute`, `/banlist`, `/Location` and `/Inventory`), and all staff can post to and read `-text` staff chat. A moderator is an ordinary player who moderates others: the warps (`/warp`, `/warptome`, `/warpmeto`, `/warpscript`) are administrators', and only an administrator may pardon or warp themselves (`pardonSelf`, `warpSelf`). `/pardon`, `/IPlookup`, `/save`, `/Refresh`, IP bans (`/BanIP` and `/unbanip`), `/chatlog`, `/auditlog`, `/CheatFile` (audited on each use), `/drop`, `/setclass`, `/roster`, `/spawn`, and the World Editor, NPC Editor, and the Control Panel with its Server Settings page are administrators' too. A command anyone lacks the permission for is answered as an unknown command. `/kick`, `/IPlookup`, `/warp` and `/warptome` refuse a target who outranks the staff member, so staff of equal rank can still kick or look up each other; `/pardon`, like the bans, jails and mutes below, needs the staff member to outrank the target (`mayTarget`). `/warpscript` never warps a speaker who outranks the staff member. Commands use the account's role as it stands, and administrative actions use [admin persistence](../../packages/server/src/persistence/admin.ts) for account lookups and audit rows. A missing target or jail map is reported rather than silently trusting a supplied destination.

### Bans, jails and IP bans

`/ban`, `/jail`, `/mute` and `/banip` take an optional duration and reason after the name. Durations such as `30m`, `7d` and `perm` are parsed by `parseModerationArgs`; a missing one uses the `banLength`, `jailSentence`, `muteLength` or `ipBanLength` setting. Every staff action is written to the moderation log with the staff member's name and the name of their role at that moment, and the bans, IP bans, jails and mutes in force are kept in their own tables until they end. A ban, IP ban, jail sentence or mute that runs out by itself is logged as ended by `system` (reason "Expired", dated when it ended), by `expireModeration` once a minute and at startup. `/banlist` pages its bans 10 at a time and lists the first 10 jails and mutes; IP bans and addresses appear only for a role with `/banip`. Staff can ban, jail, mute or pardon only those they outrank, and a role with `overrule` (administrators) can act on anyone but themselves (`mayTarget`). Only the staff member who made a ban, jail or mute, or a role with `overrule`, can change its length or lift it (`mayChange`), so a moderator can no longer overwrite an administrator's ban to lift it.

`/chatlog <name> [count] [channel]` prints a character's newest logged chat (see the [Chat guide](chat.md#the-chat-log)), including the IMs sent to them. It needs the `chatlog` permission (anyone else is told it is an unknown command), it covers every channel, and each lookup is audited.

`/auditlog <name> [count]` prints the newest staff actions (default 10, up to 100) taken by that character's account or done to that character. [`auditTrail`](../../packages/server/src/persistence/admin.ts) merges the audit log with the moderation log, which supplies bans, jails, mutes, IP bans, unmutes and pardons with their reasons, and leaves out the audit log's copy of those. It needs the `auditlog` permission, and each lookup is audited.

A jailed or muted player is told in the chat box until when, at once and at each login. Every way of talking (local chat, `/me`, broadcasts, IMs, guild chat, rooms, staff chat, mail and boards) asks [`silenced`](../../packages/server/src/systems/chat/speech.ts) first: a muted player says nothing, a prisoner is heard only on the jail map (a jailed staff member keeps staff chat, which reaches only staff), and either may still IM staff. A mute also refuses player-shop commands, which are typed into chat; a prisoner can still run them. `chatWait` and `broadcastWait` in the same file let a role with the bypass permissions skip the chat and broadcast cooldowns. A mute is on the account, runs in real time and is lifted by `muteTick` when it ends. A banned player reads the alert and the ban's end at login; the reason is shown only to staff, through `/banlist`. An account ban and an IP ban are checked after the password, and IP bans never stop a role with `bypassIpBan`. An IPv6 address bans its /64. The server records the addresses each account logs in from, so `/banip <name>` can ban the latest or every one, and a new IP ban disconnects matching sessions immediately. A jail sentence is stored and runs in real time. An offline prisoner is placed in jail at login, and one whose sentence ended while away goes to their respawn point (the fallback point if its map is gone). `/warp` refuses a map that does not exist. Staff warps cannot move a prisoner out of jail or a player into it.

Staff chat (`-text`) uses a dedicated colour (`CHAT_COLOR.staff`), has no house sender restriction, muffling, or ignore filtering, and reaches only staff recipients. A muted staff member cannot post to it. `-text` from a non-staff player gets "Only staff can use staff chat." and the input clears; `/warpscript` from anyone without the permission is an unknown command, and the line returns to the input. `/warpscript` matches whole keywords in broadcast message content only (ignoring case, never matching speaker names, protocol wrappers, or substrings) and warps the speaker to the first matching online staff member in login order, skipping staff who are in an editor, ignore the speaker or are outranked by them, and, for a speaker who is not staff, staff on the jail map.

Login attempts are counted over five minutes and account creations over an hour; a zero setting disables the corresponding limit. The counts are in memory and reset on restart. A successful password removes that attempt and clears the account-and-address count. A role with `bypassLoginLimits` is not stopped by an address that has used up its count, but only while its account has no failure from that address in the window, so a spent address gets one try at a staff password, not a run of guesses. The roster command sets one of four map slots; spawn places a rostered creature immediately on the faced tile. The drop command accepts a recognised item, with a count of up to 9,999 for a stack (`DROP_MAX`), or any positive amount of gold, and puts the pile on the faced tile.

A staff member entering an editor leaves the map until returning. A world save checks map fields, exits, text and item names, replaces its editor-managed items and roster, and refreshes players on the map; other ground drops and loot are preserved. The Fat brush paints a plus of five tiles, clipped at the map's edges, faction checkboxes (W/M/A) are mutually exclusive, clicking a lit layer button (including S) keeps that layer selected, and loading a map without an exit resets the exit fields. NPC loading combines the file with live shop stock and gold and displays the complete text losslessly. Saving validates the selected NPC and its lines, replaces its file and resets its shop ledger; open shop and bio windows for it close. The editor lists and validations are in the shared files listed above.
